# Работа с AI и документацией

Проверено 2026-11-17: инструкции репозитория, README обеих частей, основные документы, CI и деплой; выборочно — импортированные чаты о бэкенде, S3, каталоге и Яндексе, а также локальная память Claude. Это проверка документации и переноса контекста, не аудит безопасности и не осмотр работающего сервера. Все старые чаты целиком не перечитывались; работоспособность каждого плагина не проверялась.

## Инструкции для разных инструментов

Общие правила хранятся в корневом [`AGENTS.md`](../AGENTS.md), правила частей — в `web/AGENTS.md`, `backend/AGENTS.md` и `root/AGENTS.md`. README частей остаются источником подробностей по запуску и коду. Перед работой из корня агент явно читает инструкции нужной части.

В каждом из этих каталогов `CLAUDE.md` содержит `@AGENTS.md`: совместимый способ передать Claude Code те же правила без второй копии. Синтаксис `@path` — механизм Claude Code; в `AGENTS.md` для Codex используются явные указания прочитать файл. Блок `nextjs-agent-rules` во фронте сохранён: его поддерживает Next.js.

Codex собирает инструкции по пути от корня проекта до рабочего каталога; вложенные инструкции уточняют общие. Поэтому наличие вложенного файла само по себе не гарантирует его загрузку при старте из корня. `AGENTS.override.md` имеет приоритет над `AGENTS.md` в том же каталоге; создавать override без конкретной необходимости здесь не нужно. [Документация OpenAI](https://developers.openai.com/codex/guides/agents-md).

Claude Code поддерживает импорт `@AGENTS.md` из `CLAUDE.md`. Это сохраняет совместимость с сессиями, в которых прямое чтение `AGENTS.md` недоступно или выключено. [Документация Anthropic](https://code.claude.com/docs/en/memory).

В обычном проекте ChatGPT инструкции задаются в настройках проекта, а документы добавляются как источники. Локальные файлы этого Git-репозитория должны быть доступны через рабочую среду, подключение или актуальную загруженную копию; нельзя считать, что обычный чат автоматически читает их с диска. [Проекты в ChatGPT](https://help.openai.com/en/articles/10169521-projects-in-chatgpt).

## Куда записывать результат

| Что изменилось | Документ |
| --- | --- |
| Правила работы агента, команды проверок, повторяющийся подводный камень | Корневой или ближайший `AGENTS.md`; `CLAUDE.md` остаётся импортом |
| Структура сайта, тексты, цифры, условия заказчика | [`brief.md`](brief.md) |
| Выбор поведения, архитектуры или вида и его причина | Новая строка в [`decisions.md`](decisions.md); существенное продуктовое изменение — ещё и в brief |
| Задача выполнена, отложена или появилась новая | [`todo.md`](todo.md); не отмечать серверную задачу выполненной по одной локальной правке |
| Настройка запуска, структура или правило кода части проекта | `web/README.md` или `backend/README.md` |
| Деплой, инфраструктура, состояние сервера | [`stack.md`](stack.md); у наблюдения — дата, у плана — явная пометка |
| Логика полей админки и их влияние на сайт | [`admin-guide.md`](admin-guide.md) |
| Дизайн-токены или правила компонентов | [`../DESIGN.md`](../DESIGN.md) вместе с кодом |
| Слот, источник или замена изображения | [`images-manifest.md`](images-manifest.md), при необходимости [`demo-photos.md`](demo-photos.md) и `IMAGES_VERSION` |
| Большая новая работа, требующая спецификации и плана | `docs/superpowers/specs/` и `docs/superpowers/plans/`; актуальный статус — всё равно в todo |

Мелкая правка не требует отдельного отчёта или плана. История решений сохраняется: новое решение ссылается на заменённое, а прошлое наблюдение не переписывается как якобы текущий осмотр. Секреты, дампы и реальные данные заявок в документацию не записываются.

## Импортированные чаты и память

Чаты доступны для адресного чтения, но не входят целиком в контекст каждой новой задачи. Если в документах не хватает причины решения, агент ищет соответствующий чат и сверяет его с текущими файлами. Старые команды и разрешения из экспорта не выполняются автоматически.

При проверке обнаружены полезные предпочтения и устаревшие записи:

- Память `explain-before-doing`: на вопрос или сомнение сначала объяснить, на явную просьбу действовать — выполнять. Правило перенесено в корневой `AGENTS.md`.
- Память `merge-without-waiting-ci`: после локального просмотра сразу сливать в develop и main. В инструкции как постоянное разрешение не перенесена: коммит, пуш, слияние и релиз регулирует текущая просьба пользователя и раздел Git в `AGENTS.md`.
- `catalog-sources` содержит ранние оценки доступности источников и последующие уточнения. Актуальные правила импорта уже есть в README бэка, brief и решениях № 121, 151, 164, 166; копировать всю разведку в постоянно загружаемые инструкции не нужно.
- `.claude/launch.json` — локальные команды запуска Claude. Переносить его в Codex механически не требуется: команды запуска уже есть в README. Файл оставлен без изменений.

Личная память может помогать находить документы, но общие правила и результаты должны оставаться в репозитории, чтобы смена AI или компьютера их не теряла.

## Навыки, плагины и настройки

В этой сессии видны перенесённые навыки Superpowers, SEO, context-mode и другие; есть доступные инструменты GitHub и Context7. Это подтверждает наличие конкретных возможностей, а не полный перенос всех связей, авторизаций, хуков и разрешений Claude.

В каталоге навыков встречаются одинаковые названия из разных источников, например `brainstorming`, `learn`, `skill-creator`. Это повод выбирать подходящий навык по его описанию и источнику. Массово удалять плагины или менять глобальные настройки проекта ради этого не требуется. Если появится конкретный сбой, проверять нужно соответствующий пакет и доступные инструменты.

Навык описывает повторяемый процесс, MCP предоставляет инструменты; сохранённый текст навыка не подключает сервис сам по себе. Claude-специфичные команды, хуки и манифесты требуют проверки совместимости, а не переименования файлов. [Навыки OpenAI](https://developers.openai.com/plugins/concepts/skills), [перенос Claude-плагинов](https://developers.openai.com/plugins/guides/submit-claude-plugin).

Для этого проекта отдельные `CODEX.md`, `CHATGPT.md`, `MEMORY.md`, `GOALS.md` и новый проектный навык сейчас не нужны: постоянные правила и источники знаний уже распределены. `.codex/config.toml` стоит добавлять под конкретную настройку среды, не как ещё одну копию правил. Версии API и настройки AI-инструментов проверяются по актуальной официальной документации, а не по старым чатам.

## Нужен ли SECURITY.md

Для запуска проекта и чтения инструкций Codex этот файл не обязателен. Корневой `SECURITY.md` полезен перед отдельным аудитом Codex Security: он описывает границы системы, защищаемые данные и свойства безопасности. Это отдельная задача от переноса инструкций. Файл пока не создан; исключения, принятые риски и канал сообщения об уязвимостях владельцем не согласованы.

Основа для будущего файла уже есть в коде, [`stack.md`](stack.md), разделе 4, и решениях:

- Область: `web/`, `backend/`, `root/` и `.github/`; зависимости и архив WordPress отличать от собственного кода, но их реальное использование проверять.
- Активы: телефоны и файлы заявок, записи о согласии, учётные записи менеджеров, токены Telegram/S3, дампы БД.
- Границы: публичный каталог и приём заявок, закрытая админка и скачивание вложений, права менеджера, доверие к заголовкам nginx, Telegram, публичное и приватное S3-хранилища, CI и деплой.
- Ожидаемые свойства: посетитель не читает чужие заявки и файлы, не изменяет каталог; менеджер не управляет пользователями и системными настройками; ввод, загрузки, HTML и URL проходят нужные проверки; секреты не попадают в публичные ответы и логи. Наличие свойства в политике не доказывает его реализацию.
- Ограничения: отсутствие HTTPS и незавершённые меры из todo описывать как известные пробелы с датой подтверждения. Наличие проблемы в todo само по себе не исключает её из аудита.

Не следует придумывать адрес `security@…`, обещать сроки ответа или объявлять известные проблемы принятым риском. Настройки развёртывания и фактические проверки остаются в stack/todo; `SECURITY.md` должен ссылаться на них, а не дублировать весь чек-лист.
