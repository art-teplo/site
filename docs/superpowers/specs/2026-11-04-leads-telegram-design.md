# Заявки и уведомления в Telegram — дизайн

Согласовано в чате 2026-11-04. Почта, S3 и вебхук — не в этом шаге.

## Зачем

Любой путь на сайте заканчивается заявкой (brief.md). Сейчас `LeadForm` отправку имитирует. Нужно, чтобы заявка сохранялась на бэке и сразу доходила до менеджеров, а менеджеры видели, кто какую взял: сейчас они договариваются между собой и путаются.

## Что решили

**Заявка (`apps/leads`, модель `Lead`).** Имя, телефон +375 (храним `+375XXXXXXXXX`), способ связи (звонок / Viber / Telegram), комментарий, студия и город (анкета партнёра), файл до 50 МБ (PDF, JPG, PNG, XLS, XLSX), источник (`source`), страница, контекст (ответы квиза, товар с вариантом). Согласие по Закону РБ № 99-З: время, IP, версия текста согласия — оператор обязан доказать, что согласие было. Ответственный: имя и @ник из Telegram, время.

**Приём — `POST /api/leads/`**, multipart, без авторизации. Honeypot `website` (заполнен → 201 без сохранения), throttling по IP, серверная проверка телефона (как на фронте: `375(25|29|33|44|17)` + 7 цифр), расширения, размера и сигнатуры файла. Имя файла на диске — UUID, исходное имя — отдельным полем.

**Файлы** — закрытая папка `/src/private` (не `/src/media`: её ASGI отдаёт открыто, пока S3 выключен), общий том для `backend` и `celery_worker`. Скачать — только из админки. S3 — следующим шагом.

**Telegram — одна закрытая группа.** Бот только пишет в группу из `BACKEND__TELEGRAM__CHAT_ID`. Доступ к заявкам = членство в группе, решает владелец; удалили из группы — нет ни новых заявок, ни истории.
- После сохранения Celery отправляет сообщение (текст + кнопка «Беру») и файл ответом на него. Повторы при сетевых ошибках и 429/5xx; отправленное повторно не шлётся.
- «Беру» → сообщение «Взял: Имя (@ник)», кнопка «Отказаться», ответственный в админке. Двое нажали разом — заявку получает один.
- «Отказаться» — только тот, кто взял; заявка свободна, бот пишет ответом «Заявка № N снова свободна» (правка сообщения уведомления не даёт).
- Нажатия из чужих чатов игнорируются. `/start` в личке → «служебный бот». `/chatid` в группе → id чата для `.env`. Добавили в чужую группу при заданном `CHAT_ID` → бот выходит.
- Нажатия принимает сервис `telegram_bot` (long polling, команда `runbot`): только исходящие соединения, одинаково локально и на сервере. Обработка обновлений отделена от способа получения — переход на вебхук не трогает логику.
- После ревью (2026-11-04): бот на aiogram 3 внутри бэка, телефон — django-phonenumber-field, валидаторы — в `apps/core/utils.py`, тексты — `telegram/texts.py` (decisions.md № 81а, 88–90).
- Правка ответственного в админке обновляет сообщение в группе.
- После ручной проверки (2026-11-04): в сообщении нет строки «Страница», у товара — ссылка «Открыть товар на сайте» (`BACKEND__SITE_URL` + путь), на кнопке — «Отказаться (Имя)»; в админке источник подписью, страница ссылкой, вместо id Telegram — статус (decisions.md № 91–93).

**Хранение** — 12 месяцев (`BACKEND__LEADS__RETENTION_DAYS=365`), задача Celery beat раз в сутки удаляет заявки и файлы.

**Фронт.** `LeadForm` шлёт в API, если задан `NEXT_PUBLIC_API_URL`; без него — имитация, как сейчас (демо на Vercel не ломается). Файл до 50 МБ, подсказка про ссылку на облако. В согласии и политике — передача данных менеджерам через Telegram (трансграничная передача, ст. 9 99-З) и срок 12 месяцев. Текст юридически не проверен.

## Не делаем сейчас

Почта, S3/RustFS, вебхук, кнопка «Передать» (бот не знает список участников группы; «Отказаться» + «Беру» покрывают), статусы заявки, удаление сообщений в Telegram (бот может удалять только в первые 48 ч — для этого автоудаление в настройках группы).

## Что от владельца

Два бота в @BotFather (тестовый и боевой — боевой на заказчика или с передачей владения), токен — сам в `root/.env`, закрытая группа, `/chatid` → `BACKEND__TELEGRAM__CHAT_ID`, затем Allow Groups → Off. Два админа группы.
