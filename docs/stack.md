# Стек и инфраструктура art-teplo.by

Что делает сайт — см. [brief.md](brief.md). Разработчик один, работа с AI — по [ai-workflow.md](ai-workflow.md).

Разделы 1–4 сохраняют исходный проект архитектуры и целевые меры; часть предложений отложена или заменена. Например, imgproxy и MinIO сейчас не используются, HTTPS ещё в чек-листе. Реализованная схема — в разделе 7 и коде, последние записанные наблюдения сервера имеют отдельную дату; оставшиеся задачи — в [todo.md](todo.md). Перечень мер ниже не означает, что они все внедрены.

## 1. Выбор

| Слой | Выбор | Почему |
| --- | --- | --- |
| Бэкенд | Django + DRF | админка из коробки, ORM, зрелая экосистема |
| Админка | django-unfold | современный вид, инлайны, фильтры, загрузка файлов |
| Фронт | Next.js (React, App Router, TypeScript) | серверный рендеринг для SEO, ISR для каталога, анимации и плавный скролл (Framer Motion / GSAP, Lenis) |
| БД | PostgreSQL | JSONB для характеристик, GIN-индексы, полнотекстовый поиск хватит без Elasticsearch |
| Кэш и очередь | Redis | кэш API, брокер Celery, счётчики rate limit |
| Фоновые задачи | Celery | отправка заявки в Telegram и почту, обработка видео, пересчёт цен |
| Файлы | S3-совместимое хранилище (MinIO или внешний провайдер) | фото и видео не лежат на диске приложения |
| Картинки | imgproxy перед S3 | ресайз и WebP/AVIF на лету, кэш в nginx; в хранилище только оригинал |
| Вход | nginx | TLS, раздача, кэш, ограничения |

Почему Next, а не Vue/Angular: каталогу нужен SSR, анимации на React делаются быстрее всего (больше готовых примеров и библиотек), и с этим стеком Claude ошибается реже. Angular тяжёл для сайта такого размера. Если появится причина уйти на Vue, Nuxt даёт то же самое.

## 2. Контейнеры (docker compose)

```
internet → nginx ─┬─ /          → next      (node, standalone)
                  ├─ /api/      → django    (uvicorn, ASGI)
                  ├─ /admin-xxx → django    (закрыт, см. раздел 4)
                  └─ /img/      → imgproxy → S3 (кэш nginx)

django, celery ── postgres
              ├── redis
              └── S3 (media, private + public бакеты)
```

| Сервис | Порты наружу | Заметки |
| --- | --- | --- |
| nginx | 80, 443 | единственный публичный сервис |
| next | нет | `output: "standalone"`, ISR; сброс кэша вебхуком из Django при правке в админке |
| django | нет | uvicorn (ASGI, 2 воркера), миграции отдельным one-off контейнером `migrate` |
| celery | нет | worker (prefork, 2 процесса); beat — для задач по расписанию (сроки, курс валют) |
| postgres | нет | том + ночной бэкап |
| redis | нет | с паролем, `maxmemory` с политикой `volatile-lru`: вытесняется только кэш (ключи с TTL), брокер Celery — в отдельной БД redis и без TTL |
| imgproxy | нет | подписанные URL, чтобы нельзя было гонять произвольные размеры |
| minio | нет | если не внешний S3 |

Для API и фронта один домен: Next ходит в Django по внутренней сети, браузер — через `/api/` на том же домене. CORS не нужен.

Окружения: `root/docker-compose.yaml` (прод, образы из GHCR) + `root/docker-compose.infra.yaml` (postgres, redis); `root/docker-compose.dev.yaml` — поверх прода для локальной разработки (сборка из `backend/`, код смонтирован, runserver, порты наружу). Подробнее — раздел 7.

## 3. Данные и файлы

- Фото товаров, проектов, блога: публичный бакет, в БД хранится путь; в HTML — URL imgproxy нужного размера. Оригинал не отдаём.
- Видео шоурума — файл MP4/WebM до 250 МБ без перекодирования, постер загружают отдельно (решение 106); раздача с поддержкой range-запросов. Видеообзоры серий — такие же файлы у серии (решение 160).
- Файлы из заявок (планы квартир, спецификации): **приватный** бакет, наружу только временные подписанные ссылки для менеджеров.
- Характеристики товара: `Product` + `Variant`; характеристики в JSONB по схеме категории (`Category.attribute_schema`), в БД — GIN-индекс по часто фильтруемым полям.
- Проект ↔ серия: `Project.series` — необязательная M2M на `catalog.Series`; фото проекта — инлайн `ProjectPhoto`.
- Кэш: списки и фильтры каталога в Redis с инвалидацией при сохранении товара; страницы — ISR в Next.
- Бэкапы: `pg_dump` ночью в отдельный бакет с версионированием, хранение 14–30 дней; бакет с медиа — версионирование включено. **Восстановление проверить один раз до запуска.**

## 4. Безопасность

**Периметр**
- Только HTTPS (Let's Encrypt), редирект с 80, HSTS.
- Заголовки: CSP (строгий, с nonce от Next), `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, запрет iframe для своего сайта (кроме виджета Яндекса на входе).
- На хосте: ufw (только 22, 80, 443), SSH только по ключам, fail2ban; контейнеры не от root, образы с фиксированными версиями.
- Postgres, Redis, MinIO не публикуют порты — только внутренняя сеть docker.

**Админка**
- Нестандартный путь вместо `/admin/` (`BACKEND__ADMIN_PATH`, тот же путь в nginx).
- Группа «Менеджер» (`apps/core/groups.py`): заявки — смотреть и назначать ответственного, контент сайта и каталога — полностью, настройки сайта — только смотреть. Пользователи, группы и расписание задач — только у суперпользователя. Права группы задаются в коде и выставляются заново после каждого `migrate`: правка группы в админке живёт до следующего деплоя.
- Лимит попыток входа (`django-axes`): 5 неудачных под одним логином с одного IP — блок на час. Снять раньше — удалить запись в «Попытки доступа» или `axes_reset_username <логин>`.
- Пароль — от 12 символов. 2FA и basic auth на nginx пока не ставим (решение 112): при лимите попыток и сложных паролях они почти ничего не добавляют, а менеджерам мешают.

**API**
- Публичный API только на чтение; запись — одна точка приёма заявок.
- DRF throttling + лимит в nginx на `/api/leads/`.
- Заявка: honeypot-поле, серверная проверка телефона (+375), капча без трекинга (Yandex SmartCaptcha или Cloudflare Turnstile) при подозрительной активности.
- Загрузка файла: лимит размера, белый список расширений и проверка реального MIME, имя файла заменяется на UUID, антивирус (ClamAV в контейнере) — по желанию, приватный бакет без исполнения.

**Секреты и зависимости**
- `.env` не в git, в репозитории только `.env.example`; `SECRET_KEY`, пароли БД и S3, токен Telegram-бота — только оттуда.
- `DEBUG=False`, `ALLOWED_HOSTS`, `SECURE_*` и `CSRF_TRUSTED_ORIGINS` настроены; cookie `Secure`, `HttpOnly`, `SameSite=Lax`.
- Обновление зависимостей: Dependabot/Renovate + `pip-audit` / `npm audit` в CI.
- Ошибки и логи: Sentry (self-hosted или облако), логи nginx и Django в stdout, ротация.

**Персональные данные** (Закон РБ № 99-З)
- Согласие под формой логируем: время, текст согласия, IP.
- Срок хранения заявок и файлов — определить (например, 12 месяцев) и чистить задачей Celery.
- Куда уходят данные: Telegram и внешний S3 — это передача данных за границу. Если хостинг и бакет не в РБ, это надо проверить на соответствие закону. Не юридическая консультация, вопрос к юристу или в НЦЗПД.

Да, на этом стеке 2 vCPU и 4 ГБ хватит для запуска. Это оценка по типичному потреблению, не замер.

**Диск: 30 ГБ** (замер 09.11). Система 3–5 ГБ; образы одного релиза ~1,3 ГБ (backend 0,4, web 0,36, postgres 0,42, nginx+redis 0,15), на время деплоя два комплекта — `deploy.sh` чистит старые `docker image prune -f`; Postgres < 1 ГБ; swap 2 ГБ; логи и временный дамп 1–2 ГБ. Итого 10–13 ГБ, запас вдвое. Условие — медиа в S3, а не на диске.

Чем можно забить диск:

- Спам заявками с файлами. Файл до 50 МБ, DRF пускает 20 заявок в сутки с IP: 1 ГБ/сутки с одного адреса, с десятка адресов — 10 ГБ/сутки. Файлы лежат в томе `private_media` на диске и живут 365 дней. Защита: `limit_req` в nginx, алерт на диск, при первом спаме — капча.
- Логи Docker без лимита. По умолчанию `json-file` растёт бесконечно; при 50 запросах/с только nginx пишет ~1 ГБ/сутки. Лимит — в `daemon.json` (чек-лист ниже).
- Медиа из админки до включения S3: фото и видео шоурума (до 250 МБ) ложатся в контейнер.
- Образы с разными тегами: откат по тегу оставляет старые образы — `prune -f` удаляет только образы без тега. Раз в месяц `docker image prune -a` или смотреть `docker system df`.
- Дампы Postgres, если отправка в S3 упала и файлы копятся локально.

**Логи: сколько хранятся при лимите.** Лимит по размеру, не по времени: `max-size=20m`, `max-file=5`, `compress=true` — до 100 МБ на контейнер (ротированные файлы сжаты, реально меньше), на 9 контейнеров — не больше ~1 ГБ. Строка access-лога ~250 байт. Обычный день (фронт на Vercel, в nginx только API, админка и медиа) — порядка 10–20 тыс. запросов, 2,5–5 МБ: история nginx ~1–2 месяца, beat и бота — дольше. Под атакой 50 запросов/с история сжимается до пары часов, но диск цел. Логи — для разбора недавнего, не архив; нужна долгая история — выносить в отдельный сервис.

Риски:

Процессор. На 2 ядрах упрётесь, когда imgproxy на лету режет AVIF. Отдавайте WebP, оставьте длинный кэш в nginx, и после первого прогона нагрузка уйдёт. Перекодирования видео в стеке нет, это тоже помогает.
Сборка. Next и Docker-образы собираются в CI, не на сервере. Иначе сервер встанет на npm build.
Одна машина. Stage-окружения нет. Потренироваться и проверить миграции придётся локально.
Что сделать, чтобы запас не кончился:

Поставить mem_limit на каждый контейнер, чтобы один сервис не положил остальные.
Включить swap на 2 ГБ.
После запуска посмотреть docker stats под нагрузкой. Если памяти не хватит, поднять до 6 ГБ, это примерно +28 BYN в месяц без НДС. Сервер можно пересобрать без простоя в посекундной тарификации, но как именно делается апгрейд, я не проверял.


**ActiveStorage** (S3-совместимый, ДЦ Tier III в Беларуси), цены с налогами: до 100 ГБ — 0,17 BYN/ГБ в месяц; 100–300 ГБ — 0,15; 300 ГБ–1 ТБ — 0,14; свыше — 0,11. 1000 PUT — 0,01; 10 000 GET — 0,01. 50 ГБ ≈ 8,5 BYN в месяц. Трафик в прайсе не тарифицируется. Класс один, «горячий» (холодного нет). Оценка для нас: 3–6 BYN в месяц.

**Как устроено (проверено 2026-11-13 в тестовом периоде).** Endpoint `https://io.activecloud.com`, регион не нужен (бакет отвечает `default`), адреса path-style: `io.activecloud.com/<бакет>/<ключ>`. Ключи — одна пара на аккаунт, в `.env` (`BACKEND__S3__ACCESS_KEY_ID`/`SECRET_ACCESS_KEY`). Работают: bucket policy, подписанные ссылки, версионирование, lifecycle, `Cache-Control` при загрузке. CORS не настраивали — не нужен (`<img>` и оптимизатор Next).

| Бакет | Доступ | Версии | Правило | Что лежит |
| --- | --- | --- | --- | --- |
| `art-teplo-media` | политика `s3:GetObject` для всех, список закрыт | да | старые версии — через 30 дней | фото из админки (`STORAGES['default']`), кэш год |
| `art-teplo-private` | закрыт, подписанные ссылки на 5 мин | да | старые версии — через 30 дней | файлы заявок (`STORAGES['private']`) |
| `art-teplo-backup` | закрыт | да | копии — через 14 дней | дампы Postgres (`root/backup.sh`) |

Удалённый файл заявки ещё 30 дней живёт старой версией в `art-teplo-private` — срок хранения файлов фактически 365 + 30 дней.

Посмотреть руками: профиль AWS CLI (`aws configure --profile activecloud`, затем `aws configure set endpoint_url https://io.activecloud.com --profile activecloud`), `aws s3 ls s3://<бакет>/ --recursive`, версии — `aws s3api list-object-versions --bucket <бакет>`.

**Бэкап базы.** `root/backup.sh`: `pg_dump -Fc` внутри контейнера postgres → проверка `pg_restore --list` → `s3://art-teplo-backup/db/art-teplo-<дата-время>.dump` через образ `amazon/aws-cli` (на сервер ничего ставить не нужно). Копирует его на сервер `deploy.yml` вместе с `root/`. Запуск — cron пользователя `deploy`: `30 3 * * * /opt/art-teplo/backup.sh >> /opt/art-teplo/backup.log 2>&1`. Дамп локальной базы — 0,9 МБ.

Восстановление (проверено 2026-11-13 на локальной базе: серии, варианты, заявки и миграции совпали):

```bash
aws s3 cp s3://art-teplo-backup/db/<файл>.dump ./restore.dump --profile activecloud
docker compose stop backend celery_worker celery_beat telegram_bot
docker compose exec -T postgres sh -c 'dropdb -U "$POSTGRES_USER" "$POSTGRES_DB" && createdb -U "$POSTGRES_USER" "$POSTGRES_DB"'
docker compose exec -T postgres sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --no-owner' < restore.dump
docker compose up -d
```

Проверить копию, не трогая рабочую базу: `createdb restore_check`, `pg_restore -d restore_check`, сравнить счётчики, `dropdb restore_check`.

**Алерты.** `root/monitor.sh` раз в 5 минут (cron пользователя `deploy`) проверяет: диск `/` занят меньше 80 %; последний `ok` в `backup.log` моложе 26 часов; `/` и `/api/health/` через nginx отвечают 200 (две проверки подряд — деплой перезапускает контейнеры); нет упавших и `unhealthy` контейнеров проекта (`migrate` с кодом 0 не считается). Пишет в Telegram только при смене состояния («🔴 …» и «✅ снова в порядке»), о незакрытой беде напоминает раз в сутки; состояние — в `/opt/art-teplo/.monitor/`. Нагрузка — `df`, два `curl` и `docker ps`, без своих сервисов и контейнеров. Бот — свой, не бот заявок (`MONITOR__TELEGRAM_BOT_TOKEN`), чат — личный чат админа с ним (`MONITOR__TELEGRAM_CHAT_ID`): менеджеры алертов не видят, а сообщения не зависят от бота заявок. id чата: написать боту `/start`, затем `./monitor.sh chatid`. Не поймает, что лёг весь сервер или сеть: для этого нужна внешняя проверка (UptimeRobot и т. п.) — после домена.

Включить: на сервере вписать в `.env` `MONITOR__TELEGRAM_BOT_TOKEN` (свой бот из @BotFather) и `MONITOR__TELEGRAM_CHAT_ID` (написать боту `/start`, затем `sudo -u deploy /opt/art-teplo/monitor.sh chatid`), проверить — `sudo -u deploy /opt/art-teplo/monitor.sh test`. Пользователь подтвердил получение тестового сообщения 20.11.2026; расписание и автоматическое срабатывание проверок отдельно не проверялись. Скрипт и cron приезжают с деплоем (раздел 7, «Деплой»).

## 6. Решения

1. **S3: ActiveStorage, не MinIO.** MinIO занял бы диск сервера по 0,89 BYN/ГБ без резервирования и забрал бы память; хранилище провайдера дешевле, живёт отдельно от сервера и находится в РБ (снимает часть вопроса про передачу данных за границу). Тестовый период 2026-11-13: подписанные ссылки, закрытые бакеты, политика, версии и lifecycle работают; трафик в прайсе не тарифицируется. Второй пары ключей с правом только на запись в бакет бэкапов пока нет — спросить у ActiveCloud.
2. **Видео: своё видео шоурума — файл MP4/WebM до 250 МБ в админке, у серий — видеообзор тем же файлом (решения 106, 160).** Перекодирование ffmpeg отложено, пока не понадобится.
3. Капча: после первых спамовых заявок.
4. CI/CD: GitHub Actions → образы в GHCR → `docker compose pull && up -d` по SSH. Как устроено — раздел 7.
5. Админка: отдельный путь, закрыт на nginx (см. раздел 4).

**Бэкенд.** Настройки — из env с префиксом `BACKEND__` (django-environ). `BUILD_MODE=1` — сборка образа без секретов и БД (collectstatic). ASGI: Starlette отдаёт `/static/` (запечено в образ), остальное — Django. Запуск: `startservice` (uvicorn), Celery — `python3 -m celery -A settings worker|beat`. Есть `GET /api/health/` (БД + кэш), схема API — `/api/schema/` и `/api/schema/swagger/` (в проде только для staff). Админка — на пути `BACKEND__ADMIN_PATH`.

**Образ бэка.** Builder на `python:3.14-slim` + uv ставит только основные зависимости, собирает статику и байткод. Runtime — distroless `ubuntu/python:3.14-26.04`: нет shell, процесс от `_daemon_`, код только для чтения. Команды Django: `docker compose run --rm backend <команда>`.

**Заявки.** `apps/leads`: `POST /api/leads/` (multipart, throttling 3/мин и 20/сутки на IP, honeypot, проверка телефона и сигнатуры файла) → Celery `notify_lead` → закрытая группа Telegram. Файлы — в `/src/private` (том `private_media`, общий для backend и celery_worker), не в `/src/media`, который ASGI отдаёт открыто; скачать — только из админки. Бот — aiogram 3 внутри бэка: сервис `telegram_bot` (команда `runbot`, `Dispatcher.start_polling`) принимает нажатия, Celery отправляет через тот же `aiogram.Bot`; хендлеры работают с `Lead` через асинхронный ORM Django. Обработка от способа получения не зависит — для вебхука хватит адреса в Django с `Dispatcher.feed_update`. Beat раз в сутки удаляет заявки старше `BACKEND__LEADS__RETENTION_DAYS` (365).

**Контент.** `apps/content`: настройки сайта (django-solo), вопрос-ответ, проекты (с дополнительными фото), блог, галерея шоурума; API только на чтение (`/api/site/`, `/api/faq/`, `/api/projects/`, `/api/posts/`, `/api/showroom/`). Текст статей — редактор Unfold (Trix), HTML чистит `nh3`. Без S3 фото лежат в `/src/media`, в форме `ImageAsset` фронта с адресом от хранилища: на диске `/media/…` без домена (Next ходит в бэк по `http://backend:8000`, этот хост браузеру не виден), в S3 — полный адрес. Видео шоурума — файл MP4/WebM до 250 МБ в «Настройках сайта» (плюс постер); на сайте постер с кнопкой, файл грузится по нажатию. `/media/` отдаёт Starlette с поддержкой Range (перемотка, Safari); `runserver` в dev Range не умеет. Фронт кэширует ответы по тегам (`web/src/data/api.ts`); после сохранения или удаления записи Celery шлёт `POST /api/revalidate` на Next с тегом раздела и секретом.

**Справочники каталога.** `apps/catalog`: категории (картинка товара без фона), бренды (логотип SVG/PNG/WebP, «гарантия до, лет»), сроки изготовления по сериям (бренд, серия, дни; дата «Обновлено» — по последней правке). API: `/api/categories/`, `/api/brands/`, `/api/lead-times/`, тег кэша `catalog`. Там же каталог: серии, варианты, цвета и группы цветов, витрина, фото и файлы серий, курсы валют (`/api/series/…`); серии и варианты заводит импорт прайса `import_price`. Без `API_URL` фронт показывает демо-серии из `web/src/data`.

**nginx.** Единственный порт наружу. `/api/`, `/<ADMIN_PATH>/`, `/static/`, `/media/` (локальное хранилище без S3) → backend; `/` → `web:3000` (Next). Тело запроса — до 55 МБ (файл заявки до 50 МБ), в админке — до 260 МБ, ответ ждём до 5 минут (видео шоурума и серий до 250 МБ). `X-Forwarded-For` nginx заменяет на `$remote_addr`, а не дописывает, и в DRF `NUM_PROXIES = 1`: клиент не может подставить свой IP (обход троттлинга, журнал согласий). TLS и лимит на `/api/leads/` — при запуске сервера.

**CI** (`ci.yml`, на каждый PR и push в `main`; push в `develop` не запускает — всё проверено в PR): проверяется только изменённая часть, итог — задача `ci-ok`. В PR изменённые файлы берутся из PR, при push в `main` — относительно прошлого состояния `main` (не `develop`: после релиза они совпадают, и образ не публиковался бы). В `main` — только через PR `develop → main`.
- backend: ruff, `manage.py check`, `makemigrations --check`, pytest на Postgres;
- web: `npm run lint`, `npm run build`;
- root: `docker compose config` для прода, dev и dev с профилем web;
- образы backend и web собираются на каждом PR (проверка Dockerfile). Из `main` публикуются `ghcr.io/art-teplo/site-backend` и `site-web` с тегами `main` и `sha-<7>` — каждый, только если менялась его часть; задача `cleanup` оставляет по 5 последних версий.
- лимиты бесплатного плана для приватного репозитория: Actions — $12 в месяц (около 2000 минут Linux, прогон CI около 11 минут); GHCR — 500 МБ хранения (вместе с артефактами Actions) и 1 ГБ скачиваний в месяц; сжатый образ бэка около 75 МБ, фронта — 357 МБ в распакованном виде (сжатый меньше), сервер при деплое качает только изменённые слои.

**Деплой** (`deploy.yml`, вручную). Секреты — только в `.env` на сервере. Запуск только из `main` (проверка в workflow). В GitHub — секреты и переменные **репозитория** (секреты окружений в приватном репозитории на бесплатном плане недоступны): secrets `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`; variables `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_PATH`. Workflow копирует `root/` (кроме `.env`), запускает `deploy.sh`: вход в GHCR временным `GITHUB_TOKEN`, `compose pull`, `up -d --wait` (ждёт healthcheck), сброс кэша страниц фронта (`POST /api/revalidate` со всеми тегами изнутри контейнера web), чистка старых образов, перезапуск nginx, если поменялось что-то в `root/nginx/` (шаблон читается только при старте контейнера; отпечаток — в `.nginx.sha`), расписание в crontab пользователя `deploy` — бэкап в 3:30 и алерты раз в 5 минут (блок между метками `# art-teplo: begin/end` переписывается каждый раз, свои строки вне блока не трогаются).

**Что на сервере руками — только `.env`.** Скрипты, compose, nginx и cron приезжают с деплоем: на сервере их не правят и не копируют, меняют в репозитории. Руками — один файл `/opt/art-teplo/.env` (секретов в git нет): `sudo -u deploy nano /opt/art-teplo/.env`, новые переменные — по `root/.env.example`; после правки переменных бэка — `sudo -u deploy docker compose up -d` в `/opt/art-teplo`, скрипты (`backup.sh`, `monitor.sh`) читают `.env` сами при каждом запуске. Откат — тот же запуск с тегом `sha-…`: тег один на оба образа, а `sha-` есть только у образа, который в этом коммите менялся, и только у 5 последних — откатывать коммитом, где менялись оба, иначе `main`.

**Подготовить сервер (один раз):** пользователь `deploy` в группе `docker`, вход только по ключу; Docker с compose; лимит логов в `/etc/docker/daemon.json` до первого `up` (действует только на новые контейнеры): `{"log-driver": "json-file", "log-opts": {"max-size": "20m", "max-file": "5", "compress": "true"}}`, затем `systemctl restart docker` (тот же лимит прописан в compose через `x-logging`, `daemon.json` — страховка для `docker run` и сервисов без блока); swap 2 ГБ; каталог `DEPLOY_PATH` с `.env` по `root/.env.example` (новые пароли, `chmod 600`); `ssh-keyscan` хоста — в `DEPLOY_KNOWN_HOSTS`; первый суперпользователь — `docker compose run --rm backend createsuperuser`.

### Перенос каталога, наполненного локально

Релиз образов и перенос данных — отдельные операции. Сначала сделайте резервную копию серверной БД, разверните релиз и проверьте, что `migrate` завершился, а API отвечает. Перенос ниже рассчитан на каталог, где на сервере нет рабочих записей, кроме справочников из миграций.

1. **Локально выгрузите каталог** из уже наполненной базы. Команда ниже запускается из `root/` и пишет JSON на хост:
   ```bash
   docker compose -f docker-compose.yaml -f docker-compose.dev.yaml exec -T backend \
     python3 manage.py dumpdata catalog --natural-foreign --natural-primary > /tmp/catalog.json
   ```
   Для переноса связанных проектов добавьте `content.Project content.ProjectPhoto` после `catalog`, только если сверили проекты на обеих сторонах. Заявки, пользователи и настройки сайта в эту выгрузку не входят. Держите выгрузку вне Git.
2. **Сверьте файлы.** Дамп содержит ключи файлов, а сами файлы хранятся отдельно. Если обе среды используют один и тот же публичный бакет ActiveStorage, достаточно проверить наличие объектов по ключам, в том числе фото категорий и типов, логотипов, галерей, схем и документов. Если бакеты различаются, перенесите недостающие объекты с сохранением ключей. Для файлового хранилища нужен отдельный перенос файлов и настроенный постоянный том.
3. **Проверьте идентификаторы и загрузите.** У совпадающих справочников сравните slug и PK, у проектов — также записи и связи. `loaddata` сопоставляет записи без естественных ключей по PK и может перезаписать существующую запись. При расхождении сначала проверьте загрузку на копии БД и подготовьте сопоставление ключей. После сверки передайте файл на сервер вне репозитория. Из каталога Compose:
   ```bash
   docker compose run --rm -v "$PWD/catalog.json:/tmp/catalog.json:ro" backend shell -c \
     $'from django.core.management import call_command\nfrom apps.content.signals import muted_revalidation\nwith muted_revalidation():\n    call_command("loaddata", "/tmp/catalog.json")'
   ```
4. **Обновите кэш фронта.** Команда выше временно подавляет сигналы обновления кэша, чтобы не ставить задачу в очередь на каждую запись. После успешной загрузки обновите теги один раз из каталога Compose:
   ```bash
   docker compose exec -T backend python3 manage.py shell -c      "from apps.content.tasks import revalidate_frontend; revalidate_frontend('catalog'); revalidate_frontend('projects')"
   ```
5. **Проверьте результат.** Откройте `/api/categories/`, `/api/brands/` и `/api/series/?category=radiatory` на адресе нового сайта. В браузере проверьте фильтр типа и бренда, несколько серий с ценой, фото и PDF, а также перенесённые связи с проектами, если они включены в выгрузку.

Для переноса готового каталога достаточно выгрузки и файлов. `loaddemo` предназначен для отдельной локальной базы, а команды импорта прайсов — для последующих обновлений по подтверждённым исходникам.
